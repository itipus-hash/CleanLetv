# 开发文档：乐视 X4-65S 桌面定制与修改

> 本文档记录 **CleanYourTV 桌面（`com.gathin.tvhome`）在乐视 X4-65S 上的全部定制点、固件机制与修改方法**。  
> 改代码、改主题、改按键之前先读本文；上手步骤看 `使用指引.md`，固件机制的分析在第 4 章。  
> 实测机型：乐视 X4-65S（DemeterUHD，Android 6.0 / SDK 23，MStar 芯片，1920×1080，density 1.5，已 root）。  
> 最后更新：2026-10-23

---

## 0. 一分钟总览

这台电视上的桌面不是在原版上游代码上"装个主题"就完事的，固件有四层机制会和桌面打架，全部已处理：

| # | 固件机制                                     | 现象                               | 解法                                                               | 代码位置                                                |
| - | ---------------------------------------- | -------------------------------- | ---------------------------------------------------------------- | --------------------------------------------------- |
| 1 | `PhoneWindowManager` 按 keycode 拦截遥控器键    | Le 键弹出乐视视频/截图，应用收不到              | 改 `/system` 的 `.kl` 重映射 scancode→F5（不是 MENU，MENU 会弹目标 App 自己的菜单） | `dbg/fixkl.sh` + `MainActivity.handleLeKey`         |
| 2 | 固件强杀占 HOME 角色的 App                       | 任何 App 到前台约 0.5s 后桌面被 force-stop | 不停留在 Home 任务里开系统页（独立任务）；不保活                                      | `MainActivity.openSettings`（FLAG_ACTIVITY_NEW_TASK） |
| 3 | 固件连**无障碍宿主**一起强杀                         | 桌面在后台时收不到任何按键，App 级全局监听全部失效      | root 守护进程 `lekeyd` 直接读 `/dev/input`（§4.7）                        | `dbg/lekeyd/`                                       |
| 4 | 原厂桌面 `com.stv.launcher` 是 PERSISTENT 杀不掉 | 设置页返回落到乐视原生界面                    | `pm disable-user --user 0`                                       | 一次性 adb 操作                                          |
| 5 | 常驻 TYPE_PHONE 窗口盖住面板                     | 设置面板启动了但看不见                      | `pm disable com.stv.globalsetting/.service.GlobalSettingService` | 一次性 adb 操作（`tools/letv-buttons.sh`）                 |

另外本机有两个**环境特性**会坑所有调试：logcat 全局过滤 `D/` 级（调试打点必须用 `Log.i`）；adbd 的 SYNC 协议挂死（传文件必须用 `tools/b64push.py`）。

### 1.2 构建（Git Bash，在 `launcher/` 下）

```bash
export ANDROID_HOME=<你的 Android SDK 路径>
export JAVA_HOME="C:/Program Files/Android/Android Studio/jbr"
./gradlew assembleDebug testDebugUnitTest
```

- 当前版本：`versionName 2.6` / `versionCode 7`；`minSdk 23`（为这台 Android 6.0 电视特意从 26 降的，`build.gradle` 里有注释，改回去要想清楚）；`targetSdk 34`。

- 单测是纯 JVM 测试（`src/test`），模块卡片校验器，跑一遍不亏。

### 1.3 安装（必须走 b64push，不能 adb push/sync）

这台固件的 adbd SYNC 协议会挂死（10KB 都传不动），且固件删了独立 `base64` 命令（`b64push.py` 已内置 busybox 回退）：

```bash
export MSYS_NO_PATHCONV=1
cd .
./tools/venv/Scripts/python.exe -I tools/b64push.py launcher/app/build/outputs/apk/debug/app-debug.apk /data/local/tmp/tvhome.apk
adb -s 192.168.199.126:5555 shell "pm install -r -d /data/local/tmp/tvhome.apk"
```

安装后**必须**做装机收尾（force-stop 会连带关掉同进程的无障碍服务）：

```bash
adb -s 192.168.199.126:5555 shell "am force-stop com.gathin.tvhome; settings put secure enabled_accessibility_services com.gathin.tvhome/.HomeKeyService; settings put secure accessibility_enabled 1; sleep 2; input keyevent 3"
```

最后那个 `input keyevent 3`（HOME）不能省：force-stop 后焦点经常被乐视屏保 `com.stv.screenflyter` 抢走，发 HOME 键最稳地把桌面唤回。

## 3. 按键链路（应用侧）

`MainActivity.dispatchKeyEvent()` 的分发顺序（**顺序即优先级**）：

```
handleSettingsKey     → scancode 357 或 keycode 176 → openSettingsPanel()
handleLeKey           → scancode 189 → onLibraryRequested()   （应用库；377 是分享/截图键，固件自己截，到不了这里）
handleMenuKey         → keycode 82（其余来源，即真菜单键 139）→ showTileMenu()          （磁贴右键菜单）
handleInputSourceKey  → scancode 187 → 信号源面板 / 输入列表
```

要点：

1. **scancode 匹配优先于 keycode**。本机输入源键 `key 187 VIRTUAL_NUMBER` 在 Android 侧**根本没有 keycode**，只能靠 scancode 匹配——这是 `input_source_scancodes` 配置项存在的原因。Le 键被改写成 MENU 后 keycode 和真菜单键撞车，也只能靠 scancode 区分。
2. **scancode 是什么**：`KeyEvent.getScanCode()` 返回的是 **Linux EV_KEY 码**，等于 `.kl` 文件里的 `key N`。`getevent -l` 打印的 `MSC_SCAN`（如 `0x7003c`）是 USB HID 层的另一套编码，`KeyEvent` 永远不返回它。取证必须 `cat /system/usr/keylayout/<设备专属>.kl` 看 `key N` 行（`Generic.kl` 只有 `key 139 MENU` 一条，不可靠）。
3. **ADB 注入验不了 scancode 路径**：`input keyevent` 注入的事件不带 scancode，无障碍服务也不接注入事件。scancode 相关行为只能 `sendevent` 或真人按键验证（§7）。
4. **设置键双路径兜底**：`HomeKeyService`（无障碍，开机自恢复）优先消费；服务被 force-stop/重装清掉后，Activity 内 `handleSettingsKey` 兜底，两条路径行为一致。
5. **`input keyevent 82` 注入只验 keycode 路径**（弹磁贴菜单），不能证明 Le 键链路通。

## 4. 固件机制（本机定制的地基，改动前必读）

### 4.1 输入事件怎么到达应用：.kl 查找顺序

```
内核 event 节点（/dev/input/eventN）
  → InputReader 查 keylayout：先 /system/usr/keylayout/<Vendor_x_Product_y>.kl，
    找不到再 /data/system/devices/keylayout/ 同名文件，最后 Generic.kl
  → scancode 按 .kl 的 "key N 名字" 翻成 Android keycode
  → PhoneWindowManager.interceptKeyBeforeQueueing（固件有机会在这里吃掉键）
  → 分发到焦点窗口 / 无障碍服务
```

本机输入设备（`dumpsys input` 取证）：

| device | 名称                            | 节点     | keylayout 文件                             |
| ------ | ----------------------------- | ------ | ---------------------------------------- |
| 2      | LETV Smart IR Receiver（红外接收器） | event0 | `Vendor_3697_Product_0001.kl`            |
| 4      | Nanosic LETV_REC_C（蓝牙遥控键盘）    | event2 | `Vendor_4c65_Product_3d4c.kl`            |
| 3      | 同 ids 的指针设备                   | —      | keyboardType=0，**须排除**                   |
| 1      | MCE IR Keyboard/Mouse         | —      | `Generic.kl`                             |
| 5      | MStar Smart TV Keypad（机身按键）   | —      | `Vendor_3697_Product_0002.kl`（无 377/189） |

**/system 全在前、/data 永不被读**（只要 /system 文件存在）——这条规则证伪了"/data 放同名 .kl 阴影覆盖"的方案，别重试。

### 4.2 Le 键根因：固件按 keycode 吃键（2026-10-23 定案）

固件 `PhoneWindowManager.interceptKeyBeforeQueueing` **按 keycode** 拦截两个键，所有分支返回 -1（消费），应用层和无障碍层永远收不到：

| scancode | 原 keycode        | 固件行为                                                                                                              |
| -------- | ---------------- | ----------------------------------------------------------------------------------------------------------------- |
| 377      | 4415 `LETV`      | `takeScreenshot(100, 0)` —— **分享/截图键，保持原样**（§4.4b）                                                                |
| 189      | 4431 `LE`        | `sendCloseSystemWindows("lekey")` + `startService(com.stv.lekey)` + `startActivity(com.letv.tv/.WelcomeActivity)` |
| 167      | 173 `DVR` / 4409 | `startService(com.letv.openmic/closemic.with.hardware → com.stv.voice/.WindowService)` —— 包不存在，只剩两声"滴嘟"（§4.6b）    |

前置门是 `WindowManagerExt.isIgnoreFuncKeyEvent` 和 `mBlockFuncKeys`（`device_provisioned=1` 时为 false，不拦）。**与 scancode 无关——改 keycode 即可绕过**。重映射目标选 **F5（135）**：框架对 F5 没有特殊分支，且几乎没有电视 App 绑定 F5。**不要选 MENU**——第一版就是 MENU，结果在别的 App 里按 Le 会弹出那个 App 自己的选项菜单（用户报的"按下去，居然是出现菜单项目"）。


**只改 189 和 167，377 保持 LETV**：377 的固件行为本来就是要保留的截图（用户 2026-10-23 报"设置键下面的分享键怎么变成应用库了"）。两个键都改成 F5 是早期的错误做法，`fixkl.sh` 已改回并会把 F5 状态的 377 修复成 LETV。167（语音键）→ F6，见 §4.6b。

### 4.3 三条被证伪的路线（都别再试）

1. **/data 阴影覆盖**：AOSP 6.0 查找顺序 /system 在前（§4.1），/system 文件存在时 /data 永不被读。
2. **KCM 键盘布局覆盖层**（`setCurrentKeyboardLayoutForInputDevice`，需 signature 权限，root uid 0 可过 check）：Android 6.0 的覆盖层文件是 **KeyCharacterMap（.kcm）格式**——`type OVERLAY` + `key <keycode标签> {...}`，只改 keycode→字符，**不能改 scancode→keycode**。塞 .kl 内容报 `E KeyCharacterMap: <descriptor>:6: Expected key code label, got '116'`。整条路线放弃。
   - 顺带记录（备用技术）：root 调框架隐藏 API 用 `su -c "CLASSPATH=<dex> app_process /system/bin <MainClass>"`（裸 dalvikvm 缺框架 JNI 会 `UnsatisfiedLinkError: BinderInternal.getContextObject`）；取 InputDevice 用 `IInputManager.getInputDevice(int)`（AIDL 方法，`InputDevice.getInputDevice` 静态方法不存在）；持久化状态文件 `/data/system/input-manager-state.xml` 的 descriptor 格式 `vendor:<十进制>,product:<十进制>`。相关死代码（`KeyboardLayoutReceiver`、`res/raw/kl_*`、`res/xml/keyboard_layouts.xml`）已从 APK 删除。
3. **应用层/无障碍层监听**：拦截发生在 InputReader→PhoneWindowManager，事件根本到不了应用。

### 4.4 定案方案：/system 可写 + 直改 .kl（最干净，2026-10-23）

**关键发现：`su -c 'mount -o rw,remount /system'` 可行**——ext4、无 dm-verity、安全启动不校验 /system 内容。重启后挂载状态自动回 ro，**但文件内容改动持久**。（之前"删不掉开机视频"的结论就是没先 remount。）

```bash
su -c 'mount -o rw,remount /system'
sh /data/local/tmp/fixkl.sh     # 备份 + sed 重映射 + 修权限，幂等
reboot                         # .kl 开机时读取，必须重启生效
```

`dbg/fixkl.sh` 对两个遥控设备的 .kl 做三件不同的事（幂等）：

```sh
# 分享/截图键（设置键下面那颗）：保持/恢复成 LETV，交给固件自己 takeScreenshot
sed -i 's/^key 377[[:space:]].*$/key 377     LETV/' /system/usr/keylayout/$f.kl
# Le 键：改成 F5，绕过固件的 keycode 拦截，交给桌面/lekeyd 开应用库
sed -i 's/^key 189[[:space:]].*$/key 189     F5/' /system/usr/keylayout/$f.kl
# 语音键（分享键下面那颗）：改成 F6，桌面拿它开用户指定的 App（§4.6b）
sed -i 's/^key 167[[:space:]].*$/key 167     F6/' /system/usr/keylayout/$f.kl
chown root:root ...; chmod 644 ...
# f = Vendor_3697_Product_0001（红外 event0）+ Vendor_4c65_Product_3d4c（蓝牙 event2）
```

- 备份：设备 `/data/local/tmp/kl-backup/`，PC `dbg/kl-backup-orig/`（MD5 已核对）。
- **重刷固件后必须重跑 fixkl.sh**（.kl 会恢复原样）。
- **377 绝对不要改成 F5**（2026-10-23 用户报"分享键怎么变成应用库了"）：那颗键的固件行为就是截图，改成 F5 等于把它从截图变成应用库。`fixkl.sh` 现在会把已经是 F5 的 377 改回 LETV，所以跑一遍就能修复。
- 应用侧只认 **scancode**，不认 keycode（改映射不影响）：`MainActivity.handleLeKey`、`HomeKeyService.onKeyEvent`、`lekeyd` 现在都**只认 189**（377 已从三处移除）；真菜单键 scancode 139 不受影响（仍开磁贴菜单，2026-10-23 实测）。
- 应用库弹窗（`AppLibraryDialog`）额外把 **F5 当作"退出"**（和 MENU 一样关库），因为弹窗独占键盘，事件到不了 Activity。

### 4.4b 分享键（截图）走的是固件自己的 takeScreenshot（2026-10-23 恢复）

scancode 377 保持 `LETV`（keycode 4415）后，`PhoneWindowManager.interceptKeyBeforeQueueing` 里那支 `4415 -> takeScreenshot` 就照常工作：

- 截图存 `/sdcard/Pictures/Screenshots/Screenshot_YYYYMMDD-HHMMSS.jpg`（**jpg，不是 png**）。
- 截完固件自己弹一个"截图成功！保存在：本机存储/Pictures/Screenshots/"的对话框，两个按钮 **完成 / 查看**。它盖在任何 App 之上，会短暂打断当前界面——这是原厂行为，不是我们引入的。
- 全局有效：桌面内、文件管理器里都实测能截（2026-10-23）。
- 验证时**必须用 `sendevent` 注入真实 scancode**（`input keyevent 4415` 只能证明固件能力，证明不了 .kl 映射对不对）：

```bash
su -c 'sendevent /dev/input/event0 1 377 1; sendevent /dev/input/event0 0 0 0; \
       sendevent /dev/input/event0 1 377 0; sendevent /dev/input/event0 0 0 0'
```

### 4.5 固件强杀 Home + 原厂桌面 PERSISTENT

- 任何 App/设置页到前台约 0.5s 后，AMS 主动 `Force stopping com.gathin.tvhome`（pid 2320 = system_server 自己，不是外部 am force-stop）。只针对占 HOME 角色的 App。框架里有 `TvMasterManager`（在 boot.oat，任何进程可调，`isIllegalApp/addIllegalApp/clearIllegalApps`），本机未装电视管家（`mTvMaster == null`），判定规则在框架里，**App 侧无法绕过，不要试图保活**。
- 正确做法是让返回路径确定性回到 Home：① 系统设置页必须用 `FLAG_ACTIVITY_NEW_TASK` 开在**独立任务**里（`MainActivity.openSettings`/`SystemSettings`）——并进 Home 任务会被连同任务一起销毁，页面闪一下就没了；② 设置页返回时栈为空 → AMS 解析 HOME → 重启我们的桌面（冷启动约 640ms）。
- **原厂桌面 `com.stv.launcher`（T2Launcher，`/system/app/T2Launcher/T2Launcher.apk`）是 PERSISTENT、uid 1000 常驻**，`am force-stop` 杀不掉；只要它开着，设置页返回必然落到它上面（用户报的"返回是乐视原生界面"就是这个）。已 `pm disable-user --user 0` 禁用（重启后保持）。恢复：`su -c 'pm enable com.stv.launcher'`。

### 4.6 常驻 TYPE_PHONE 窗口盖住面板

乐视 `com.stv.globalsetting/.service.GlobalSettingService` 常驻一个 `ty=2008`（TYPE_PHONE）窗口，**永远压在 TYPE_APPLICATION（ty=1）之上**——我们的设置面板确实启动了、焦点也是我们的，但被整层盖住。代码层面无解，已禁用该服务（Activity 不禁，乐视自己的系统设置 App 照常可用）。封装在 `tools/letv-buttons.sh` / `.ps1`（幂等，勿再动）。

### 4.6b 语音键（scancode 167）：改成一键开 App（2026-10-23 定案走路线 A）

遥控器上分享键下面那颗语音键，2026-10-23 查清：

- 映射：红外 `key 167 DVR`、蓝牙 `key 167 RECORD`（同一个 scancode，两个标签）。蓝牙遥控经固件转成 keycode **4409（0x1139）**，红外是 **173 DVR**。
- 固件在 InputReader 就打点：`E/InputReader: get record key and set property`；随后 `PhoneWindowManager.interceptKeyBeforeDispatching` 的 `startRecord` / `stopRecord` 各起一个服务：
  - 按下：`act=com.letv.openmic.with.hardware cmp=com.stv.voice/.WindowService`
  - 松开：`act=com.letv.closemic.with.hardware cmp=com.stv.voice/.WindowService`
- **本机没有 `com.stv.voice` 这个包** → `ActivityManager: Unable to start service ... : not found`。所以按下去只有固件自己放的两声"滴嘟"，没有任何界面（用户 2026-10-23 的原话："目前按下去 会滴嘟两下，哈哈"）。
- 固件是**按 keycode** 拦的（`interceptKeyBeforeDispatching`），所以和 Le 键一样，改 .kl 换 keycode 就能绕过，把事件交给应用层。

三条路线：

| 路线                  | 做法                                                                                                    | 结论                               |
| ------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------- |
| **A. 改成普通快捷键（已采用）** | `.kl` 把 167 改成 **F6**，桌面里定义动作                                                                         | ✅ 2026-10-23 实现并实测：一键打开用户指定的 App |
| B. 自建语音壳            | 新建包名 `com.stv.voice` 的 App，声明 `.WindowService` 接 `com.letv.openmic/closemic.with.hardware`，自己做录音+识别界面 | 未做：要写语音 App，服务端也多半已停             |
| C. 装原版 APK          | 找乐视 `com.stv.voice` 装上                                                                                | 未做：包不好找                          |

**为什么选 F6**：两份 .kl 里 F6 只被 scancode 64（USB 键盘的 F6）占用，167 是空的；框架对 F6 没有特殊分支，也没有电视 App 绑定它。**两声"滴嘟"保留**——用户明确说"挺好听"，而且它是这颗键唯一的按键反馈（固件那段 `startService` 失败不影响按键本身）。

**交互（`MainActivity.handleVoiceKey`）**：

| 状态                       | 按下语音键                                                                       |
| ------------------------ | --------------------------------------------------------------------------- |
| 没设置过（`voice_key_app` 为空） | 弹「语音键要打开哪个 App？」列表 → 选中即保存**并立刻打开**，让按钮自证                                   |
| 已设置                      | 直接打开那个 App（`AppPicker.launch`，按 App 自己声明的 LEANBACK/LAUNCHER 入口，不重启已运行的 App） |
| 选过的 App 被卸载/禁用           | Toast「xxx 已经打不开了，请重新选一个 App」，清掉旧值并弹列表                                       |
| 电视端改                     | 设置键 → 桌面设置 → **语音键 App** 一行，弹同一个列表；选「未设置」= 清掉，下次按重新引导                       |

- 匹配用 **scancode 167 或 keycode F6** 二者之一：`.kl` 改写后 keycode 是 F6、scancode 仍是 167；`input keyevent 136` 没有 scancode，USB 键盘的真 F6 没有 167。
- 列表只列**用户自己装的 App**（`FLAG_SYSTEM` / `FLAG_UPDATED_SYSTEM_APP` 全过滤，用户原话"不要显示预装应用，谁会选那些啊"），TV 应用（LEANBACK）在前，按名称排序，桌面包自己排除。
- `voice_key_app` 在 `onResume` 重读：设置页是从快捷面板的独立任务里打开的，`onActivityResult` 不一定回来（同 §6.22 的教训）。
- **只在桌面在前台时有效**：别的 App 在前台时 F6 归那个 App（没人绑，等于没反应）；固件会杀无障碍服务（§4.7），所以**没有**做全局路径，也不打算做。

### 4.7 全局 Le 键：root 守护进程 lekeyd（2026-10-23 定案）

**需求**：在任何 App 里按 Le 都能唤出应用库，且不弹目标 App 自己的菜单。

**为什么不能用 App 实现**：固件在"另一个 App 到前台"后约 0.5s 会 force-stop **所有持有无障碍服务的包**。实测连专门新建的单服务小包 `com.gathin.tvkeys` 也一起被杀（`Force stopping com.gathin.tvkeys ... from pid 2378`、`dumpsys accessibility` 的 `services:{...}` 立刻变空），且 force-stop 让包进入 stopped 状态，**服务不会自动重新绑定**。对照组：无无障碍的 `com.stv.filemanager` 在别的 App 前台时存活。结论：App 级全局监听在本机不可行（`tvkeys` 模块已删、包已卸载）。

**方案**：`/system/bin/lekeyd`（纯 C，12KB，root 进程，不是包，固件不杀）直接读 `/dev/input/event*`，命中 Le scancode 就 `am start` 一个 `ACTION_TOGGLE_LIBRARY` 意图。

| 文件                                 | 作用                                                                 |
| ---------------------------------- | ------------------------------------------------------------------ |
| `dbg/lekeyd/lekeyd.c`              | 守护进程源码                                                             |
| `dbg/lekeyd/build.sh`              | NDK 交叉编译 + `fix-flags1.py`（**必需**，见 §9）                            |
| `dbg/lekeyd/fix-flags1.py`         | 清掉 ELF 的 `DF_1_PIE` 位，否则 Android 6 linker 拒绝加载                     |
| `dbg/lekeyd/lekeyd.sh`             | `while true` 看护 + 显式 export `ANDROID_ROOT`/`ANDROID_DATA`（`am` 需要） |
| `dbg/lekeyd/install-recovery-2.sh` | 开机自启挂点                                                             |
| `dbg/lekeyd/leplay.sh`             | 播放守卫（§4.9），部署到 `/system/bin/leplay.sh`                             |

**开机自启**：`/init.rc:680 service flash_recovery /system/bin/install-recovery.sh` 和 `/init.rc:743 service installLetvMisc /system/bin/install-recovery.sh --misc` —— **两个服务都执行同一个脚本**，所以 `/system/etc/install-recovery-2.sh`（SuperSU 的 `install-recovery.sh` 末尾调它）**每次开机会跑两遍**。脚本里等 `sys.boot_completed=1` 再 `exec sh /system/bin/lekeyd.sh`，放后台。

**单实例**：上面那个"跑两遍"导致第一版出现两个 lekeyd，一次按键触发两次 `am start`，应用库开了又关。现在 lekeyd 启动时扫 `/proc/*/cmdline` 比对第一个 argv（必须是 `/system/bin/lekeyd`，排除 `sh lekeyd.sh` 看护脚本），发现同类就 `_exit(2)`；看护脚本见到 2 就 `sleep 30` 继续观察，主实例死了能接管。

**三条路径 + 一道闸门**（`MainActivity.claimLePress()`，800ms 内只认一次）：

| 场景                 | 谁处理                                            | 方式                                                                                               |
| ------------------ | ---------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 桌面在前台              | `MainActivity.handleLeKey`（`dispatchKeyEvent`） | 直接 `onLibraryRequested()`，零延迟；**无障碍关着也有效**（2026-10-23 实测）                                        |
| 桌面在前台（服务活着）        | `HomeKeyService.onKeyEvent`                    | 同进程直调，兜底                                                                                         |
| 别的 App 在前台 / 桌面已被杀 | `lekeyd`                                       | `am start -f 0x10000000 -a ...TOGGLE_LIBRARY -n .../.AppLibraryActivity -d tvhome://toggle/<ts>` |

**守护进程怎么知道桌面在前台**：`MainActivity` 在 `onResume` 把 pid 写进 `files/foreground`、`onPause` 删掉；`lekeyd` 读文件并校验 `/proc/<pid>` 存在才认为是前台。前台就**不插一脚**（否则 `am start` 会让 Home 走一次 `onPause → onNewIntent → onResume`，把刚打开的库又关掉）。文件带 pid 是为了防止"进程被杀但文件残留"导致按钮在别的 App 里彻底失效。`AppLibraryActivity`（§4.8）复用**同一个文件**，所以面板浮着的时候守护进程同样让路，按键由面板自己的 F5 处理。

**意图必须带唯一 data URI**：`am start` 用 `--ei ts` 这种 extras 区分不了意图——AMS 用 `Intent.filterEquals()` 比较，**不看 extras**，会只把任务提到前台而不投递 `onNewIntent`（日志：`Warning: Activity not started, its current task has been brought to the front`）。带 `-d tvhome://toggle/<uptime>` 才会真正投递。

**应用库的关闭从 `onPause` 移到 `onStop`**：给已 resume 的 Activity 投递新意图时，`ActivityThread.performNewIntents` 会先 `callActivityOnPause`；关库留在 onPause 里就会"刚打开就被关掉"（这是 toggle 早期失效的根因之一）。

**部署**（详见迁移文档）：

```bash
# /system 可写，直接放系统分区
su -c 'mount -o rw,remount /system'
# lekeyd → /system/bin/lekeyd (755)
# lekeyd.sh → /system/bin/lekeyd.sh (755)
# install-recovery-2.sh → /system/etc/install-recovery-2.sh (755)
reboot
```

**验证/排障**：日志在 `/data/local/tmp/lekeyd.log`（超过 64KB 自动清空）；正常按键会打印 `scancode 189 on /dev/input/event2 -> toggle` 或 `scancode 189, home in front -> left to the desktop`。改完 lekeyd 二进制要 `kill -9 <pid>` 让看护脚本重启它（**别用 `pidof`**，见 §9）。


### 4.9 播放守卫：关掉应用库后把视频还给你（2026-10-23）

**用户报**："比如视频APP，唤出应用库的时候，怎么暂停播放了，这个是一定要暂停吗，如果一定要暂停，那么取消应用库的时候，可以继续播放吗"

**暂停是必然的，别想着绕**：只要盖上去的是 Activity（哪怕 `windowIsTranslucent`），下面的 Activity 就会走生命周期。实测红果TV：悬浮库起来后它的 MainActivity 是 **`state=STOPPED`**（不只是 PAUSED），`dumpsys media.audio_flinger` 里 `0 are active` —— 音频轨道直接没了。只有"不是 Activity 的窗口"（系统悬浮窗，`TYPE_SYSTEM_ALERT` 那种，由 root 进程 addView）才能不打断，那要重写一套窗口 UI，代价和风险（§4.6 的常驻 TYPE_PHONE 抢焦点）都不划算。

**能做的：关库时把播放还回去。** 实测红果TV 关闭后**不会**自己续播（停在 `state=2`，位置不动），但 `input keyevent 126`（媒体播放键）能让它继续。于是：

| 文件                            | 作用                                                        |
| ----------------------------- | --------------------------------------------------------- |
| `dbg/lekeyd/leplay.sh`        | `was`：开库前记下"谁真的在出声"；`resume`：关库后确认回到同一个 App 且已经没声音，补一个播放键 |
| `lekeyd.c` 的 `spawn_helper()` | 两个时机各 fork 一个 root 子进程跑上面的脚本，不阻塞输入循环                      |
| `AppLibraryActivity.onPause`  | 写 `files/library_closed`，lekeyd 主循环 250ms 内看到就触发 `resume` |

**两个判定不能省**：

1. **必须是"真的在出声"才算在播**。`dumpsys media_session` 的 `state=3` 在本机是**陈旧**的——悬浮库盖上去之后红果TV 的 session 还挂着 `state=3 / speed=1.0`，而音频轨道早就 0 了。用 `dumpsys media.audio_flinger | grep "of which [1-9][0-9]* are active"` 才是真相；播的是谁，用 `dumpsys audio` 的 Audio Focus 栈顶（`pack: <包名>`）取。
2. **必须确认回到的是同一个 App**（`top_pkg == was`）。否则从库里选一个新 App，会把播放键发到那个 App 身上。

另外 `resume` 里还要再查一次"现在有没有声音"：App 要是自己恢复了播放，再发一个播放键会把它**按停**。

**实测**：红果TV 播放中 → 注入 scancode 189 → 库浮起、`le_playing=com.hgtv.star`、`active=0` → F5 关库 → 2 秒内 `active=1`、画面字幕都回来；对照场景（文件管理器里开/关库，本来就没在播）→ 不写标记、不发按键、无副作用。

## 6. 已定稿设计决策（改代码前必读，都是用户拍板的）

1. **焦点样式：常亮描边、永不填充**。`duplicateParentState` 在本机 MStar ROM 上父子状态传递不生效——"菜单行白填充 + 子视图翻深色"会变成白底白字完全盖住（用户对此 bug 的描述是"焦点翻深色"）。解法：焦点态一律"透明底 + 2dp 白描边、文字/图标恒白"（`input_row_bg.xml`、`pill_bg.xml`、`row_text.xml`）。`RowFocus.java` 闪烁方案已废弃删除。`settings_choice_bg`（设置面板）是半透明绿填充+亮绿描边，用户明确不动。
2. **菜单弹窗关闭必须用行级 OnKeyListener**（`addMenuRow`）：focusable PopupWindow 独占键盘，Activity 的 `handleMenuKey` 收不到；面板级 OnKeyListener 不触发（panel 不可聚焦）。再按一次菜单键/返回键关闭。
3. **菜单键失灵兜底**：`lastFocusedTilePosition()`——菜单用返回键关掉后窗口可能没焦点，再按菜单键要能重开（用户报过"返回后除非按主界面返回否则菜单键失灵"）。
4. **菜单位置按视觉边界算**：`tileAt[0] + width*scaleX`（聚焦卡片视觉宽 = 布局宽 × 1.12，用布局宽会插入图标约 14px）。
5. **格内 APP 名称：聚焦时显示在 tile 下方**（2026-10-25 改）。以前普通 App 的 `name` 视图被设成 `INVISIBLE`（hero 区已经有焦点应用名，只有卡片类型和 dock 才显示），用户要求"聚焦 Dock 之外的 APP 也能在 APP 下面显示名字，切换时原有的渐变退出、下一个渐变出现"，所以 `onBindViewHolder` 现在对每个 tile 都 `h.name.setVisibility(View.VISIBLE)`——**可见性不再参与判断，只有 alpha 在动**：`Holder` 的焦点监听把名字 220ms 淡到 1.0（失焦淡到 `restNameAlpha`），同时 `translationY` 从 -6dp 滑到 +4dp，两个名字自然交叉淡化。`always_show_names: true` 的含义收窄成"失焦时停在 0.75 而不是 0"（整屏都带标签）；图标瓦片在无名字时放大居中的逻辑（`setIconSize`）没动，卡片内 `label` 对 App 仍然隐藏，名字只出现在卡片外那 22dp 的槽里。
6. **顶栏只保留三个**：Wi-Fi 胶囊、应用库、设置。输入源胶囊（`show_inputs_pill:false`）和排序按钮（`reorder_button:false`）都关掉——信号源靠遥控器 187，排序靠菜单。

24. **程序坞 = 网格第一行，只能一行；`rows_below_dock` 只决定它下面露出几行**（2026-10-23 定案，用户问"程序坞是不是只能固定一行"→ 是）：
    - **结构**：`dockSize = COLUMNS`，`DockDecoration` 只给前 `COLUMNS` 个格子画带子，`fill_dock` 用后面的 App 补齐空位。程序坞不是独立容器，做不出两行。
    - **实现**：给网格 `RecyclerView` 加 `paddingTop` 把第一行往下推，下方露出 N 行：`want = max(minTop, h - dockRow - itemH * rows)`。
    - **底边一像素都不能留**：`paddingTop` 之后剩余的空间会被"下一行"立刻占满。以前多减了 `BOTTOM_ROOM_DP`(30dp)，后果是 0 行时屏幕底部露出下一行的 45px 顶边（用户报"设置 0 还是会露出来一点"），1 行时把网格最后一个元素「应用库」胶囊切掉一半——`uiautomator dump` 里 `btnLibrary` 的 bounds 只剩 `[890,1066][1060,1080]`（14px 高，用户报"应用库图标显示不全"）。现在按整行精确贴边，下一行正好从屏幕边缘开始，完全看不见。
    - **可达上限**：`AppAdapter.maxRowsBelowDock()` = `(h - minTop - dockRow) / itemH`，其中 `minTop` = 大标题（hero）高度 + 40dp，且不小于 `TITLE_ROOM_DP`。本机 5 列 + 显示大标题时只有 **1 行**（`878 - 263 - 247 = 368`，除以 220 取整 = 1）。设置页通过 `EXTRA_MAX_ROWS_BELOW_DOCK` 拿到这个上限，把够不着的选项直接 `GONE`（现在只显示 0/1），选中项按 `min(存储值, 上限)` 显示。关掉应用库（`app_library:false`）时 `minTop` 降到 156px，上限变 2。
    - **瓦片不再因行数变小**：上限保证 `rows` 一定放得下，`tileWidthPx` 的"按高度收缩"分支走不到。以前设 3 会得到 258×143（设 2 是 298×164），而程序坞位置和 2 一模一样——用户看到的就是"设置几行都没变化"。
25. **`columns` / `rows_below_dock` 必须在 `onResume` 重读并 `recreate()`，不能只靠 `onActivityResult`**（2026-10-23 踩到，用户报"设置 0 行的时候，返回桌面并没有生效"）：这两个值只在 `onCreate` 读一次并用来算 `paddingTop` 和瓦片尺寸，而 `onActivityResult` 的 `RESULT_OK` **不一定回得来**——设置页可以通过设置键进入（`HomeKeyService` → `MainActivity` → `startActivityForResult`），固件在别的界面到前台约 0.5s 后会 force-stop Home，结果就丢了；实测复现：sp 已写成 0，桌面仍是 1 行，logcat 里 MainActivity 没有任何重建。修法：`onCreate` 记下 `builtColumns` / `builtRowsBelowDock`，`onResume` 里 `layoutChanged()` 比对（按 `Config.load` 接受的区间夹一下，避免非法值导致重建死循环），变了就 `recreate()` 并 `return`。和 §6.22 的 `showStats` 是同一类坑——**凡是只在 `onCreate` 读、又要电视端能改的值，都要在 `onResume` 复核**。
26. **往下翻就是老老实实滚一格，不要为「最后一格」做任何特殊处理**（2026-10-23 定案，**当前状态 = 已回退**）：用户先说"翻到最后一行要自动翻到底露出应用库，不然露出一半很丑"，做过三版又全部撤掉，最后原话是"往下滚动，还是默认滚动一个格子好了，不要刻意增加""也就是不要再考虑是不是最后一格的问题"。**现在 `requestChildRectangleOnScreen` 里没有任何 footer / 最后一行的判断**，滚动距离只取决于聚焦矩形和可视区，和普通格子完全一致；应用库胶囊到达底部时被切一半，这是**有意接受**的现状。
    - **不要再用"翻到最后一行就滚到底"这类自动补齐 / 吸附**：电视上用遥控器逐格移动时，多出来的距离一定会被感知成突兀（三版全被否：瞬跳"太快很突兀"、默认时长平滑"像冲刺特别不自然"、按距离定时长也只是没那么明显）。**用户要的是恒定一格的手感**，以后遇到"自动补齐 / 吸附 / 滚到底"的需求先问清再做。
    - 三条技术结论留作参考（将来真要精确控制滚动时用）：
      - **剩余距离要量 footer 自己**：`findViewByPosition(itemCount-1).getBottom() - (getHeight() - getPaddingBottom())`。**不要用 `computeVerticalScrollRange() - Extent - Offset`**：那是 `ScrollbarHelper` 按可见子项数量和平均尺寸**估算**的，网格里混着整行 footer 时算不准——本机实测少算 **82px**。
      - **`scrollBy(0, 超大值)` 能自动夹到真底，但一帧瞬跳**；`smoothScrollBy` 要距离精确，否则"平滑但没滚到底"。两者不能兼得。
      - **判断"最后一行"必须按列对齐**：`(appCount-1)/COLUMNS*COLUMNS`；用 `appCount-COLUMNS` 在最后一行不满时会把上一行也算进去。

    - **数据来源**：官方语句包 `hitokoto-osc/sentences-bundle`（GitHub / jsDelivr / `sentences-bundle.hitokoto.cn` 三个镜像），按 12 个分类分成 a–l 十二个文件，对象结构与 v1 应答一致（`hitokoto`/`from`/`from_who`/`type`/`id`/`length`…）。抓取脚本 `dbg/build-sentences.py`：每个文件重试 4 次（退避 2/4/6/8s），按 id 去重再按文本去重，输出 6 字段。**任何一个分类抓失败就写 `<out>.partial`，绝不覆盖已有文件**（曾因 CDN 抽风把 10527 条写成 284 条）。

    - **为什么按 50 字过滤**：两个展示面里更紧的是桌面右上角框（约 61 字，见下条），`length > 50` 的句子在两个面上都可能被截断，用户要求"把超过 50 字的全部删除" → 10527 → 9896 条。
    - **`Sentences.java`（package-private final class）**：`ensure()` 首次把整个 asset 读成 `byte[]`，扫描一遍建 `starts[]`/`lengths[]` 行偏移 + 每行的类别位 `bits[]`；`at(i)` 只 `new String(data, start, len)` 再 `JSONObject` 解析那一行。对外三个方法：`daily(context, day, mask)`、`random(context, mask)`、`count(context, mask)`；另有 `CATEGORIES`（12 个中文名，顺序即位序）与 `ALL = (1<<12)-1 = 4095`。
    - **同一天固定一句**：`daily()` 用 `day.toEpochDay() * 0x9E3779B97F4A7C15L` 混洗后对**命中条数**取模（不是对总条数取模，否则改类别范围会偏），所以同一天同一类别组合永远同一句；`random()` 用 `Random.nextInt(count)`，每次打开都不同。
    - **类别用位掩码**：12 个分类各占一位（动画=bit0 … 抖机灵=bit11），`4095` = 全选。设置页用 `AppPicker.showMulti()` 勾选，**最后一类不允许取消**（否则一条都取不到）。
    - **每行类别必须存 `int[]`，不能存 `byte[]`**（这次最大的坑）：`byte` 只有 8 位，bit 8–11（诗词/网易云/哲学/抖机灵）直接被截断；更阴的是 bit7（影视=128）存进 `byte` 变成 `-128`，`(byte & 256)` 时符号扩展成 `0xFFFFFF80`，`& 256` 得 256 ≠ 0 —— 于是"只选诗词"却一直出影视（实测 `count=170`，正好是影视条数）。改成 `int[] bits` / `int[] lineBits` 并去掉所有 `(byte)` 强转后，`count=713` 正确。
    - **两个消费方**：桌面 `MainActivity.loadHitokoto()`（开关 `show_hitokoto`，类别 `hitokoto_categories`）→ `Hitokoto.loadDaily()`；Le 键面板 `AppLibraryDialog.showQuote(categories)`（`le_key_function=1` 或 `home_le_key_function=1` 时，类别都是 `le_hitokoto_categories`）→ `Hitokoto.loadRandom()`。**两套类别互不影响**：`Config` 里是两个独立键（`HITOKOTO_CATEGORIES_KEY` / `LE_HITOKOTO_CATEGORIES_KEY`），`config.xml` 两个独立 `<integer>`，默认都是 4095。设置页把它们叫做「一言类别(首页)」和「一言类别(Le键)」。
    - **`Hitokoto.load()` 的兼容约定**：两个入口都仍走 `new Thread(..., "hitokoto")` + `handler.post` 回主线程，并**照旧先回调一次旧缓存**（`shared_prefs/hitokoto` 四键 `date`/`text`/`from`/`who`），再回调新句子——消费方仍按"幂等重渲染"写，别假设只来一次。
    - **`from`/`from_who` 必须先 `json.isNull()` 再 `optString`**：`optString` 会把 JSON 的 `null` 变成四个字母的字符串 `"null"`，曾让出处显示成「— null《JOJO的奇妙冒险》」（§6.29）。
    - **出处格式** `source()`：`— 作者《作品》`；作者或作品任一侧为空则省略该侧，两侧都空返回 `""`（调用方把出处行 `GONE`）。
    - **`INTERNET` 权限已删除**：本地库不需要联网，`AndroidManifest` 里原来为 hitokoto 加的 `INTERNET` 已移除（注释写着 "No INTERNET permission on purpose"）。以后再加网络功能记得补回来。
    - **`java.time.LocalDate` 是 API 26 的类**，本机 minSdk 23 能用是因为 `build.gradle` 开了 `coreLibraryDesugaringEnabled true` + `desugar_jdk_libs:2.0.4`，**别为了"API 23 没有 java.time"去改回 Calendar**。
    - **AGPL-3.0 提醒**：语句库是 AGPL-3.0，只有"通过官方 CDN 超链接方式使用"才豁免开源；**打进 APK 等于分发数据库**，需要开源 launcher 本体。已向用户说明，尚未定论——在定论前不要把 `assets/sentences.json` 打进对外发布的包。
    - **两个面的显示容量（2026-10-25 实测，`dumpsys window` 量面板边界 + 布局推算）**：桌面右上角框 `maxWidth 520dp`(780px) + 17sp + `maxLines=2` → 每行约 30 个全角字、**共约 61 字**；Le 面板宽 `min(dp(800), available-dp(64))` = **1200px**（不是全屏宽，dumpsys 实测 1200×420）、文字区 1152px + 24sp + `maxLines=3` → 每行约 32 字、**共约 96 字**。两个面共用同一缓存，**以更紧的桌面框约 61 字为准**。全量库 10527 条中 >60 字的 316 条（3.0%）、>96 字的 45 条（0.4%）；按 ≤60 字筛选可保留 97%。注意 `length` 是字符数，半角英文实际占宽减半、纯英文句能放更长，换行断句也有少量浪费，实际上限比理论值略低。

## 6.31 天气行：时钟下方一行实时天气（2026-10-25 定稿）

用户要求："首页的 10月25日 星期日 往上移 在他的位置放一个天气…城市写本地"，随后又改口"把日期放到原来的位置，天气放时间的下面"。**最终版式**：日期回到时钟右侧原位（分隔线后竖排，一个字没动），**天气行是时钟那个 `LinearLayout` 的下一个兄弟节点**，独立一行在时钟下方。

- **位置**：`activity_main.xml` 里 `weatherBox`（horizontal，`layout_marginTop="6dp"`，默认 `gone`）紧跟时钟行，内含 `weatherIcon`（20dp）+ `weather`（`0dp/weight=1`，singleLine+ellipsize=end）。不碰 hero、不碰 grid、不碰每日一语，所以**网格的 `match_parent` 和 `rows_below_dock` 完全不受影响**。
- **显示格式**：`26°泉州 · 阴 · 最高 28° 最低 24°`（温度取整、城市名、天气现象、当日最高/最低）。
- **数据源：和风天气（QWeather）新版 API**，三个端点，全部 `lang=zh`：
  - `GET https://<host>/geo/v2/city/lookup?location=<城市>&range=cn&number=1` → `location[0].name/adcode/lat/lon`
  - `GET https://<host>/weather/v1/current/<lat>/<lon>` → `condition.text/code`、`temperature.value`
  - `GET https://<host>/weather/v1/daily/<lat>/<lon>?days=1` → `days[0].temperatureMax/Min`
  - **API Host 是每帐号独立分配的**（形如 `p53tekdrpj.re.qweatherapi.com`）。公共域名 `api.qweather.com`/`geoapi.qweather.com`/`devapi.qweather.com` 官方公告 2026 年起逐步停用，**别再往主题/设置里写公共域名**。本机凭据只存在电视的 `launcher_settings` sp 里，**不内置进源码**（用户原话"填进去，别内置"）。
- **三个键都在 `launcher_settings`（sp 优先于主题 JSON）**，设置页三行位于「右上角应用库按钮」之后、「壁纸」之前：
  - `weather_api_key`：空 = 整个功能下线，`Weather.refresh()` 直接返回 null，**连连接都不开**（没 Key 就不上网）。
  - `weather_api_host`：默认 `api.qweather.com`（`Config.DEFAULT_WEATHER_HOST`）。
  - `weather_city`：**空 = IP 定位**。走 `https://myip.ipip.net`（纯文本，`来自于：` 之后按空白切，丢掉国家段和含 `.` 的运营商段，取最后一段 → 「泉州」），再把城市名喂给 GeoAPI 拿坐标。**地点缓存 6 小时**，且按 **query 字符串**（不是解析结果）比较是否变更。
- **`Weather.java`（约 340 行，新文件）**：`Snapshot{city,temp,text,code,max,min,at,place,placeAt,query}` + `Place{name,lat,lon}`；`load(Context)` 只读 `files/weather.json`（磁盘 only，主线程安全）；`stale()` = 30 分钟、`expired()` = 24 小时；`refresh()` 起 `"weather"` 线程；`iconFor(code)` 按 `code/100` 分桶 → `weather_rain/snow/haze/wind/sun/cloud`。
- **`INTERNET` 权限又加回来了**：§6.30 为本地语句库删过，天气这一行又需要联网，`AndroidManifest` 里重新声明（注释写明只为天气存在）。
- **天气三键故意不进 `syncThemeChoices()` 清理列表**：它们是凭据/设置不是主题选择，主题签名一变就把 Key 清了，天气会下线到用户重新输入。`hasOnTvChoices()` 与「跟随主题」重置同理不含这三键。
- **`MainActivity` 侧**：`onCreate` findViewById + 读 sp 城市 + `renderWeather(Weather.load(this))`；`onResume` 重读三个 sp 键（同 §6.22/§6.25 的"只在 onCreate 读就要在 onResume 复核"）；`minuteTick` 里加 `refreshWeather()`（内部比较时间戳，不产生请求）。`renderWeather()`：无 key / 缓存为 null / 已过期 / 城与温都空 → `GONE`。
- **两个只有这台电视/这个 API 才会踩的坑（都已在代码里解决）**：
  - **QWeather 强制 gzip**：服务器**始终**返回 `Content-Encoding: gzip`（不管客户端要不要），`HttpURLConnection` 不会自动解压 → 直接读流是乱码。必须按 `connection.getContentEncoding()` 包 `GZIPInputStream`（`Weather.get()`）。
  - **Android 6 TLS 锚点缺失**：专属 Host 用 Let's Encrypt，证书链 `*.re.qweatherapi.com` ← `Let's Encrypt YR2` ← `ISRG Root YR` ← **ISRG Root X1**；2015 年固件的 CA 库没有 ISRG Root X1 → `CertPathValidatorException: Trust anchor for certification path not found`。公共 `api.qweather.com` 用 Sectigo（老设备认）所以以前能通。解法：`res/raw/isrg_root_x1.pem`（1939 字节，2015-06-04 ~ 2035-06-04）+ `Weather.tlsContext()` 的委托 TrustManager——**系统锚点优先，失败了才问内置根**，所以已信任的主机行为不变。
  - **API 23 的 VectorDrawable 不支持弧线命令（A/a 要到 API 24）**：六个 `weather_*.xml` 的圆形全部用 4 段三次贝塞尔拼（kappa 0.5523），已用自写光栅化器渲染验证。
- **备份还原会冲掉天气凭据**：`backup-2026-10-25/data/launcher_settings.xml` 是加天气之前导出的，`restore.sh data` 会用旧 sp 覆盖，`weather_api_key`/`weather_api_host` 一起消失。还原后需在设置页重填（或更新备份里的 sp）。
- **实测记录（2026-10-25）**：IP 定位链路在电视上真实跑通——`myip.ipip.net` → 泉州 (24.87445, 118.67572) → `{"city":"泉州","temp":26,"text":"阴","code":104,"max":28,"min":24}`，`files/weather.json` 181 字节，首页显示 `26°泉州 · 阴 · 最高 28° 最低 24°` + 阴天图标，日期行原位未动。

### 6.31.1 天气/日期/状态行的后续定稿（2026-10-25 当天追加）

- **农历**：`Lunar.java`（约 175 行，纯 `java.util`，可脱离 Android 单测）按农历位表算 1900-01-31 起 200 年的朔闰，输出 `丙午年 九月十六`（**不带「农历」二字**，年与月之间一个空格）。挂在**日期右侧同一行**（`date` 与 `lunarDate` 在一个 horizontal 里，`date` 必须 `wrap_content`——用 `weight=1` 会把农历推到行尾），同色同字号。`Lunar.format()` 超出 1900–2100 返回 `""` → 视图 `GONE`。

## 9. 坑与禁忌（每条都踩过）

1. **`pidof` 在本机不可信**：`kill -9 $(pidof lekeyd)` 会展开成整张进程表（`1 2 3 5 ...`），杀掉一大片进程导致软重启。取 pid 用 `ps | grep lekeyd` 或 `ls -l /proc/*/exe | grep lekeyd`。
2. **NDK r26+ 编出来的二进制 Android 6 加载不了**：lld 给 PIE 打上 `DT_FLAGS_1 = 0x8000001`，老 linker 报 `unsupported flags DT_FLAGS_1=0x8000001` 并拒载。必须跑 `fix-flags1.py` 清 `DF_1_PIE`（`build.sh` 已串好）。
3. **`am start` 的 extras 区分不了意图**：AMS 用 `Intent.filterEquals()` 比较，不看 extras，只会 `Warning: Activity not started, its current task has been brought to the front`。要投递 `onNewIntent` 必须带唯一 `-d <uri>`。
4. **给已 resume 的 Activity 投递新意图会先 `onPause`**：`performNewIntents` 必调 `callActivityOnPause`。所以"关库"不能写在 `onPause`（§6.14）。
5. **`/init.rc` 里两个服务跑同一个 `install-recovery.sh`**（`flash_recovery` 和 `installLetvMisc --misc`），开机脚本会执行两遍 → 守护进程必须自己单实例。
6. **App 做不了全局按键监听**：固件在别的 App 到前台约 0.5s 后 force-stop 所有持有无障碍服务的包（§4.7）。别再去写"全局收键"的 App。
7. **`pm install -r` 会清空无障碍设置**（§6.19）：装机后必须重写两条 settings 并校验 `dumpsys accessibility`。
8. **`/system` 的 remount 会静默失败**：`mount -o remount,rw /system` 返回 0，但 `/proc/mounts` 里仍是 `ro`，写操作报 `Read-only file system`（2026-10-23 两次踩到，第一次靠重启恢复，第二次找到了真因）。**真因是 SuperSU 的挂载命名空间隔离**：普通 `su -c` 里的 remount 只作用于该会话的私有命名空间，所以返回成功、全局仍是 ro。**必须用 `su --mount-master -c "mount -o remount,rw /system; ..."`**，而且 cp/chmod 要和 remount 写在同一个 `--mount-master` 会话里。写入前先 `grep ' /system ' /proc/mounts` 确认是 `rw`，别信返回码。
9. **替换正在运行的二进制会 `Text file busy`**：先 `mv /system/bin/lekeyd /system/bin/lekeyd.old`（在跑的进程占着 inode，不受影响）→ 再 `cp` 新文件 → 再 kill 旧进程让看护脚本重启。
10. **`settings put secure` 两条不要写在一条命令里**：合在一起执行时 `enabled_accessibility_services` 会变成空值，必须分两次。**而且"写入相同的值"不会触发重新绑定**（SettingsProvider 只在值变化时通知监听者）：`dumpsys accessibility` 会一直显示 `services:{}`，看着像服务挂了。这时要先 `settings put secure enabled_accessibility_services ''` 再写回服务名——但**写空串会把 `accessibility_enabled` 一起打回 0**，所以最后必须再补一条 `settings put secure accessibility_enabled 1`，然后确认 `dumpsys accessibility` 里出现 `Service[label=主页键]`。
11. **logcat 全局过滤 `D/`**：调试打点只能用 `Log.i`。
12. **Git Bash 要 `export MSYS_NO_PATHCONV=1`**，否则 b64push 会把 `C:/...` 当设备路径。
13. **b64push 必须用 venv 的 python**（`tools/venv/Scripts/python.exe`），系统 python 缺 `adb_shell`。
14. **`dumpsys media_session` 的 `state=` 会骗人**：App 被盖住后 session 仍可能挂着 `state=3`（播放中）而音频轨道早就没了。判断"现在有没有在播"要用 `dumpsys media.audio_flinger | grep "of which [1-9][0-9]* are active"`（§4.9）。
15. **透明 Activity 一样会让下面的 Activity 停下**：不是 PAUSED 而是 **STOPPED**，`windowIsTranslucent` 不改变这一点。想"不打断"只有系统悬浮窗一条路（§4.9）。
16. **别用 `input text` 去测中文输入框**（2026-10-23 踩到）：焦点在 `EditText`、搜狗 IME 停在符号页时，`input text Fish` 注入的按键会被 IME 转成别的字符——实测把「许多鱼」写成了「许多鱼！」，还顺手把对话框关掉回到了桌面（删到空再按删除键会向上传递成 BACK）。要验证"输入框能改值"，用 `input keyevent 67` 删字符 + 直接改 `shared_prefs` 更快；真实的中文输入体验只能由用户拿遥控器验。
17. **`.kl` 里 377 和 189 不能一起改成 F5**（2026-10-23 用户报"设置键下面的分享键怎么变成应用库了"）：两颗键的固件行为完全不同——377 是**分享/截图**（`takeScreenshot`，存 `/sdcard/Pictures/Screenshots/*.jpg` 并弹"截图成功"提示），189 才是 Le。早期为了绕开固件拦截把两个都改成 F5，等于把截图键也变成了应用库。现在 `fixkl.sh` 只改 189，并把 377 一律写回 `LETV`（所以跑一遍能修复被改坏的机器）。改完必须重启（.kl 开机只读一次）。
18. **验证截图键必须 `sendevent` 377，不能 `input keyevent 4415`**：后者注入的是 keycode，绕过 .kl，只能证明"固件截图功能还在"，证明不了"377 映射对了"。同理验证 Le 键也要 `sendevent 189`（`input keyevent 135` 的 scancode 是 0，桌面侧按 scancode 匹配会忽略）。
19. **让电视待机只能用 `sendevent` 116，`input keyevent 26` / `223` 都没反应**（2026-10-23 实测）：`KEYCODE_POWER`（26）和 `KEYCODE_SLEEP`（223）注入后 `mWakefulness` 仍是 `Awake`、`Display Power: state=ON`，`mStayOn` 也是 false（不是被常亮挡住）。真实 scancode 116 一按就进待机，**adb over network 立刻 offline**，只能按遥控器电源键唤醒（没有 CEC 的话无法远程唤醒）。所以任何"定时待机"的功能都要先想好怎么唤醒。
20. **`AlertDialog.setMessage` 会把列表整个顶掉**（2026-10-23 踩到）：message 和 `setSingleChoiceItems` 用的是**同一个 body 槽位**，同时设置时只显示 message，列表根本不出现——表现是弹窗只剩标题、一句说明和一个「取消」，选 App 的列表凭空消失。要在列表上方加说明，只能用 `setCustomTitle(自定义 View)`。
21. **`setSingleChoiceItems` 的行在这台电视上不可聚焦**：`simple_list_item_single_choice` 的 CheckedTextView 没有 focusable，D-pad 进去动不了（`input keyevent 20` 按四次截图一模一样），弹窗只能取消。选 App 的列表改成自己建的、`focusable` + `focusableInTouchMode` 的 TextView 行（背景 `input_row_bg`，和磁贴菜单同一套描边），D-pad 就正常了。
22. **`AlertDialog` 会把 `setView` 的自定义视图强制成 MATCH_PARENT**：给它设 `LayoutParams` 高度没用（长列表会撑满屏幕、最后一行被切一半）。要限高只能让视图自己在 `onMeasure` 里夹（`AppPicker.MaxHeightScrollView`）。
23. **设置键（357）只存在于蓝牙 .kl**：往 event0（红外）注入 357 完全没反应，没有任何日志。要验设置入口得往 **event2** 注入。
24. **测 `shared_prefs` 驱动的布局，必须"先写 sp 再 force-stop"**（2026-10-23 踩到，浪费了一轮排查）：桌面本身就是 HOME，`am force-stop` 之后固件会立刻把它重新拉起来，这个新实例读的是**写入之前**的 sp。所以"force-stop → 写 sp → am start"的顺序会让每一档都测到上一档的结果（表现为整体滞后一位：设 1 得到 0 的位置、设 2 得到 1 的位置，还以为是代码算错）。正确顺序是 **写 sp → force-stop → sleep → am start**，并且用 `Log.i` 把 `ask/rows/pad` 打出来核对，别只看截图。
25. **`unregisterNetworkCallback` 注销没注册过的回调会崩 Activity**（2026-10-23 抓到）：`Compat.registerVpnCallback` 在 API 24 以下直接 return（本机 Android 6.0），所以 `vpnCallback` 从来没注册过；`onDestroy` 里无条件 `cm.unregisterNetworkCallback(vpnCallback)` 抛 `IllegalArgumentException: Invalid NetworkCallback`，包在 `Unable to destroy activity` 里，**每次 Activity 重建（改设置触发的 `recreate()`）都会崩一次进程**，还会连带 `unregisterReceiver` 之后的清理全被跳过。现在统一走 `Compat.unregisterNetworkCallback()`（try/catch 吞掉），`unregisterReceiver` 也包了 try/catch。
26. **`su -c 'sed -i'` 改 `shared_prefs` 会把文件写坏，而且 `ls -l` 看不出异常**（2026-10-23 踩到，差点丢掉用户全部电视端设置）：toybox 的 `sed -i` 走"临时文件 + rename"，新文件**丢了 `u:object_r:app_data_file` 的 SELinux 上下文**（属主 `u0_a44`、权限 660 全都正常，肉眼完全看不出问题）。app 进程 open 失败 → SharedPreferences 当成空文件 → `Config.load` 全部回落到主题值 → 桌面当场从 5 列变 4 列、每日一语消失、语音键 App 回默认；更糟的是紧接着一次 commit 会把空 map 写回盘（只剩 `theme_signature`），**原设置彻底丢失**。
    - **正确做法**：本地写好完整 XML → `adb push` 到 `/data/local/tmp/` → `su -c 'cp /data/local/tmp/x.xml <目标>'`（`cp` 覆盖已有文件是 `open(O_TRUNC)`，**保留 inode 和上下文**）→ `chown u0_a44:u0_a44` + `chmod 660`。要删某个键就在本地编辑后整文件覆盖，**永远不要用 `sed -i` 改 sp**。
    - 顺序仍是"先 force-stop 再覆盖"，覆盖完再 force-stop 一次把固件刚拉起的实例杀掉，然后 `am start`，否则新实例可能已经 commit 覆盖你的写入。
    - 本机 app uid = **10044**（`u0_a44`）；`ls -Z` 在 toybox 上无输出，别指望用它查上下文。
